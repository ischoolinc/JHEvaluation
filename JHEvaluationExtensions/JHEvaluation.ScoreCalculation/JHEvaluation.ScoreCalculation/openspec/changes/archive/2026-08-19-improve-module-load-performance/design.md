## Context

模組是 .NET Framework 4.8 的桌面外掛，載入入口集中於 `Program.Main()`，且在主 UI 執行緒依序完成部署模式判定、學生與教務 Ribbon 建立、ACL 套用、事件掛載、明細項目註冊及資料合理性檢查註冊。目前沒有分段計時，無法區分框架物件存取、JIT／型別載入、部署參數查詢與本模組註冊程式各自的成本；也沒有自動或可重複的功能清單來防止效能調整造成註冊遺漏。

既有功能支援新竹與高雄兩種部署模式，並依賴 FISCA、Framework、JHSchool 與 K12 的既有初始化順序。改善必須相容目前的同步 `MainMethod` 生命週期，不新增套件，也不能在背景執行緒直接操作 UI 元件。

## Goals / Non-Goals

**Goals:**

- 以相同環境、相同帳號與相同資料條件建立可重複的載入基準，量出總耗時及各階段耗時。
- 找出並改善實測的主要瓶頸，使最佳化前後結果可比較、可追蹤且可設定回歸門檻。
- 將載入流程拆成有明確責任、可計時、只執行一次的階段。
- 在縮短關鍵路徑的同時，完整保留部署模式、UI、ACL、事件與擴充點註冊行為。
- 讓延後工作失敗時可診斷，且不阻斷其餘模組載入或留下永久不可用的功能。

**Non-Goals:**

- 不調整成績計算、畢業資格、排名或報表的業務演算法。
- 不改善使用者開啟各功能後的資料查詢或報表產生效能，除非量測證明該工作目前誤在模組載入階段執行。
- 不變更 FISCA／K12 框架、部署格式、資料庫結構、公開 API 或畫面配置。
- 不以不可控的背景平行化取代所有同步註冊工作。

## Decisions

### 1. 先建立階段式基準，再選擇最佳化項目

把 `Main()` 拆成部署設定、學生功能註冊、教務功能註冊、畢業功能與報表註冊、ACL／選取事件註冊、明細項目註冊、資料合理性檢查註冊等階段。以 `System.Diagnostics.Stopwatch` 量測每階段與總耗時，輸出固定格式的階段名稱、毫秒數、結果與例外資訊。診斷輸出使用本機既有診斷管道，量測本身不得同步寫入遠端服務。

基準與改善後測試在相同版本、機器、登入帳號、部署模式及資料條件下執行；冷啟動與暖啟動分開記錄，各至少執行十次，報告中比較中位數與第 95 百分位。第一輪實作只最佳化實測占總耗時顯著比例的階段，避免以推測進行大幅重構。

替代方案是只量 `Main()` 總耗時；這無法定位瓶頸，也無法在後續回歸時指出來源，因此不採用。

### 2. 維持必要註冊同步完成，僅延後已證明非必要的昂貴工作

所有會決定載入完成時選單是否存在、權限是否正確、Click handler 是否可用及擴充點是否可被框架發現的工作仍在 `Main()` 返回前完成。只有同時符合下列條件的工作才可延後：量測證明成本顯著、框架不要求同步完成、首屏不依賴其結果、且首次使用前能可靠完成。

延後工作採惰性首次使用或框架 UI 就緒後排程；需要操作 UI 時必須回到 UI 執行緒。每項延後初始化以單次狀態保護，並具備未開始、執行中、完成、失敗等可觀察狀態。首次使用遇到尚未完成時，應完成初始化或顯示可理解的失敗資訊，不得靜默遺漏功能。

替代方案是在 `Main()` 內直接建立多個背景工作；這會引入初始化競態與跨執行緒 UI 風險，且可能只把等待移到不可預測的位置，因此不採用。

### 3. 以明確初始化單元和冪等入口降低重複成本

將長篇內嵌註冊程式抽成按責任命名的方法或小型協調類別，並在同一階段快取重複使用的 `RibbonBarItems`、`MenuButton`、ACL 結果及部署參數。頂層初始化以互鎖或等價的單次保護避免框架重複呼叫時重複建立選單、掛載事件或加入檢查器。

冪等保護只涵蓋本模組註冊，不吞掉首次初始化例外；首次失敗必須留下可診斷資訊，並依階段安全性決定允許重試或停用該非必要項目。

替代方案是只做區域變數微調而維持單一 `Main()`；雖可減少少量重複查找，但難以持續量測與驗證各階段，因此不採用。

### 4. 建立載入功能盤點與效能驗收報告

功能驗證涵蓋兩種部署模式、學生與教務成績作業、畢業作業、報表、ACL 啟閉、學生選取變更、三個明細項目、批次學期歷程與資料合理性檢查。效能驗收報告保存測試環境、樣本、各階段統計、主要瓶頸、採取的改善及前後差異。

成功門檻為：在基準中位數高於 200 ms 時，模組關鍵路徑中位數至少降低 20%，且第 95 百分位不得惡化超過 10%；若基準已不高於 200 ms，則不得為追求百分比而增加複雜度，改以總耗時中位數與第 95 百分位皆不退化、並移除已確認的重複工作作為驗收。

## Risks / Trade-offs

- [診斷計時本身增加耗時] → 使用低配置的 `Stopwatch` 與單次彙整輸出，並同時量測關閉詳細診斷時的結果。
- [冷／暖啟動及外部框架造成波動] → 固定環境與資料條件、分開統計冷暖啟動、採十次以上樣本與中位數／第 95 百分位。
- [延後初始化造成首次點擊延遲] → 僅延後非首屏必要工作，驗收同時記錄首次使用時間，必要時在 UI 就緒後預熱。
- [背景初始化觸碰 UI 或產生競態] → UI 工作保留同步或切回 UI 執行緒，並以單次狀態機保護。
- [拆分註冊流程造成權限或事件遺漏] → 先建立完整功能盤點，最佳化前後逐項驗證，並保留可快速回退的同步路徑。
- [效能收益不足以抵銷複雜度] → 設定 200 ms 分界與量化門檻，未達顯著瓶頸時只保留低風險的量測、快取與去重。

## Migration Plan

1. 在不改變行為的前提下加入分段計時與功能盤點，取得兩種部署模式的冷／暖啟動基準。
2. 依報告排序瓶頸，先做重複存取消除與初始化單元拆分，重新量測並完成功能回歸。
3. 僅對仍顯著且符合安全條件的階段導入惰性或 UI 就緒後初始化，逐項量測與驗證首次使用行為。
4. 保存前後報告與驗收結果後發布。若發生回歸，先停用對應延後路徑並恢復同步註冊；量測與低風險拆分可保留供後續診斷。

## Open Questions

- 實際宿主是否提供正式的「UI 已就緒」事件或既有模組載入效能記錄管道，需在實作前由框架 API／既有模組用法確認。
- 冷啟動自動化方式是否能由現有開發環境穩定重建；若無法，需在驗收報告中明確記載人工步驟與快取控制方式。
